### L1 · A formal checker certifies the stated theorem; audit the statement separately

`LLM / agent evaluation` · now 2.5 → target 4.5 · priority 2.00 · ~12 min

**Why today.** Alpöge released his Claude-assisted Riemann claim as a Lean proof, outlets disagree on whether it covers RH or GRH, and nobody has yet replayed the whole proof. Those are the two separate questions any machine-checked result raises: does it check, and is the checked statement the one claimed? ([Anthropic mathematician says he and Claude proved the Riemann hypothesis; Lean proof not yet independently checked](https://www.washingtonpost.com/technology/2026/11/20/using-anthropic-ai-mathematician-claims-have-solved-riemann-hypothesis/))

A proof assistant's kernel guarantees that the proof term inhabits the formal statement, assuming the axioms and the kernel are sound. It says nothing about whether that statement, together with every definition it depends on, means what the English claim says. Errors hide in definitions (a mis-specified zeta function, a wrong domain), in dropped hypotheses, or in an added axiom or 'sorry' that the checker accepts. The same split runs through agent and LLM evaluation: a passing unit-test suite or grader certifies the spec it encodes, and a weak spec lets wrong answers through, which is reward hacking under another name. In practice, review the statement and its definitions by hand, list the axioms used (Lean's #print axioms), and test the spec against deliberately bad 'proofs' that it ought to reject. The toy below shows a dropped divisibility condition letting a nonsense witness verify.

```python
# A checker certifies the statement it was given, not the one you meant.
# Claim: every n >= 2 has a certificate f with 1 < f, f | n, and (f == n or f*f <= n).
# A "proof" here is a function producing f; the checker runs the spec on every n < N.
import math

def intended(n, f):
    return 1 < f and n % f == 0 and (f == n or f * f <= n)

def weakened(n, f):                    # the formal statement silently dropped "f divides n"
    return 1 < f and (f == n or f * f <= n)

def good_proof(n):                     # smallest factor: a genuine witness
    return next((p for p in range(2, math.isqrt(n) + 1) if n % p == 0), n)

def bad_proof(n):                      # nonsense witness: always 2 (or n when n < 4)
    return 2 if n >= 4 else n

N = 50_000
for name, proof in [("good", good_proof), ("bad", bad_proof)]:
    ok_w = all(weakened(n, proof(n)) for n in range(2, N))
    ok_i = all(intended(n, proof(n)) for n in range(2, N))
    print(f"{name:4s} proof | passes weakened spec: {ok_w} | passes intended spec: {ok_i}")
# The checker's 'verified' is only as strong as the statement: audit the spec separately.
```

### L2 · MoE sizing: memory follows total parameters, compute follows active ones

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~12 min

**Why today.** Tencent's open Hy4 is reported as a MoE with about 770B total and 49B active parameters, a 15.7x gap that sets what hardware you need to serve it. ([Tencent open-sources the full Hy4 model, a 770B-parameter MoE, completing open release of its Hunyuan LLM line](https://www.ithome.com/1/029/841.htm))

In a mixture-of-experts layer a router sends each token to k of E expert FFNs, so the forward pass costs about 2 FLOPs per active parameter, the same as a dense model of the active size. Every expert must still sit in memory, because the next token may route anywhere, so weight memory scales with total parameters. Decode at small batch is bound by memory bandwidth: each step reads the active experts' weights, so latency tracks active bytes. As batch size grows, tokens spread over more experts until a step touches nearly all of them, and serving cost moves toward the dense-total regime. That trade-off is why MoE is cheap per token at scale but needs many GPUs, or expert offloading, just to load the model. The numbers below are illustrative and ignore KV cache, activations and parallelism overheads.

$$
\text{FLOPs/token} \approx 2N_{active}, \qquad M_{weights} = N_{total}\, b, \qquad t_{decode} \gtrsim \frac{\min(N_{total},\, B N_{active})\, b}{BW}
$$

```python
# MoE: memory scales with TOTAL parameters, per-token compute with ACTIVE ones.
# Illustrative numbers only, using the reported 770B total / 49B active split.
total, active = 770e9, 49e9
dense_equiv = 49e9

for name, bytes_per_param in [("BF16", 2), ("FP8", 1), ("INT4", 0.5)]:
    weights_gb = total * bytes_per_param / 1e9
    gpus_80gb = weights_gb / 80
    print(f"{name}: weights {weights_gb:,.0f} GB -> at least {gpus_80gb:.1f} x 80GB GPUs just to hold them")

flops_per_token = 2 * active          # forward pass ~ 2 FLOPs per active parameter
print(f"forward FLOPs/token ~ {flops_per_token:.2e} (same as a {dense_equiv/1e9:.0f}B dense model)")
print(f"memory/compute ratio vs a 49B dense model: {total/active:.1f}x more weight bytes per FLOP")

# Decode is memory-bandwidth bound: at batch 1 each token must read the active experts' weights.
bw = 3.35e12                           # bytes/s, illustrative HBM bandwidth per GPU
for batch in (1, 32):
    bytes_read = min(total, active * batch)  # FP8 bytes; worst case: tokens spread over different experts
    print(f"batch {batch}: ~{bytes_read/1e9:,.0f} GB of expert weights touched per step "
          f"-> {bytes_read/bw*1e3:.1f} ms on one GPU's bandwidth")
```
