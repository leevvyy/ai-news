### L1 · Write top-k sparse attention by hand and see when it fails

`AI-off fluency` · now 2.5 → target 4.0 · priority 1.50 · ~15 min

**Why today.** Alibaba says Qwen4-Max is built on a new architecture based on Qwen Sparse Attention, so it is a good moment to rebuild the basic idea of sparse attention from scratch. ([Alibaba formally launches Qwen4-Max, a 2.4T-parameter MoE with offensive-cyber data filtered out](https://www.qbitai.com/2026/11/510486.html))

Dense causal attention scores every query against every earlier key, so cost grows as O(T^2 d) in sequence length T. Top-k sparse attention keeps only the k keys with the highest scores for each query and renormalises the softmax over them, cutting the weighted sum to O(k d). The approximation is good only when the attention distribution is peaked: if a few keys carry most of the softmax mass, dropping the rest changes little. With random Gaussian queries and keys, as in the snippet, attention is nearly flat and keeping 8 of 64 keys gives a large error. This is why production schemes learn which keys to select or combine sparse attention with local windows, and why the selection step itself must be much cheaper than computing all the scores. Try making attention peakier by scaling Q up and watch the error fall.

$$
\mathrm{Attn}_k(q) = \sum_{i \in \mathcal{T}_k(q)} \frac{e^{q\cdot k_i/\sqrt d}}{\sum_{j \in \mathcal{T}_k(q)} e^{q\cdot k_j/\sqrt d}} v_i,\quad \mathcal{T}_k(q)=\operatorname{top-}k_i\,(q\cdot k_i)
$$

```python
import math, random
# Top-k sparse vs dense causal attention, pure stdlib. Illustrative sizes only.
random.seed(0)
T, d, k = 64, 16, 8                     # sequence length, head dim, keys kept per query
rnd = lambda: [[random.gauss(0, 1) for _ in range(d)] for _ in range(T)]
Q, K, V = rnd(), rnd(), rnd()

def attend(q, keys, vals):
    s = [sum(a * b for a, b in zip(q, kv)) / math.sqrt(d) for kv in keys]
    m = max(s); w = [math.exp(x - m) for x in s]; z = sum(w)
    return [sum(wi * v[j] for wi, v in zip(w, vals)) / z for j in range(d)]

errs = []
for t in range(k, T):                   # causal: query t sees keys 0..t
    dense = attend(Q[t], K[:t + 1], V[:t + 1])
    scores = [sum(a * b for a, b in zip(Q[t], K[i])) for i in range(t + 1)]
    top = sorted(range(t + 1), key=lambda i: -scores[i])[:k]
    sparse = attend(Q[t], [K[i] for i in top], [V[i] for i in top])
    num = math.sqrt(sum((a - b) ** 2 for a, b in zip(sparse, dense)))
    errs.append(num / math.sqrt(sum(a * a for a in dense)))
errs.sort()
print(f"kept {k}/{T} keys; median relative error {errs[len(errs)//2]:.3f}")
print(f"score cost per query: dense O(T*d)={T*d}, sparse O(k*d)={k*d} (+ key selection)")
```

### L2 · Compare models on cost per solved task, with a paired bootstrap CI

`LLM / agent evaluation` · now 2.5 → target 4.5 · priority 2.00 · ~15 min

**Why today.** Alibaba claims Qwen4-Max cuts average task cost by 58% versus Qwen3.8-Max (RMB26.58 to RMB11.16 per task) on its in-house Work360 evaluation. ([Alibaba formally launches Qwen4-Max, a 2.4T-parameter MoE with offensive-cyber data filtered out](https://www.qbitai.com/2026/11/510486.html))

Average cost per task ignores whether the task was solved, so a cheap model that fails more often can look better than it is. Dividing total spend by the number of solved tasks gives cost per success, which is what a user actually pays for. Because both models ran on the same tasks, the right uncertainty estimate is a paired bootstrap: resample task ids with replacement and recompute the ratio on the same ids for both models, so task difficulty cancels. The ratio of two sums is biased in small samples and its interval is asymmetric, so report a percentile interval rather than plus-or-minus. It breaks down when tasks are not exchangeable (for example a few huge tasks dominate cost) or when the evaluation set is the vendor's own and may be tuned to it.

$$
\mathrm{CPS} = \frac{\sum_i c_i}{\sum_i \mathbb 1[\text{solved}_i]},\qquad \rho = \mathrm{CPS}_A/\mathrm{CPS}_B
$$

```python
import random
# Illustrative per-task logs (cost in RMB, solved?) for two models on the same 200 tasks.
random.seed(1)
tasks = range(200)
A = [(random.uniform(15, 40), random.random() < 0.62) for _ in tasks]
B = [(random.uniform(6, 17), random.random() < 0.58) for _ in tasks]

def cost_per_success(rows):
    s = sum(ok for _, ok in rows)
    return sum(c for c, _ in rows) / max(s, 1)

obs = cost_per_success(A) / cost_per_success(B)
ratios = []
for _ in range(2000):                      # paired bootstrap: resample the same task ids
    ids = [random.randrange(200) for _ in tasks]
    ratios.append(cost_per_success([A[i] for i in ids]) / cost_per_success([B[i] for i in ids]))
ratios.sort()
lo, hi = ratios[49], ratios[1949]
print(f"mean cost/task A {sum(c for c,_ in A)/200:.2f}  B {sum(c for c,_ in B)/200:.2f}")
print(f"cost per SOLVED task ratio A/B = {obs:.2f}  (95% CI {lo:.2f}-{hi:.2f})")
```

### L3 · Separate MoE memory (total params) from compute (active params)

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~10 min

**Why today.** Qwen4-Max is reported as 2.4T total parameters with 71B active, and Tencent's Hy4 flash as 224B total with 12B active. ([Alibaba formally launches Qwen4-Max, a 2.4T-parameter MoE with offensive-cyber data filtered out](https://www.qbitai.com/2026/11/510486.html) · [Tencent releases Hunyuan Hy4 flash: 224B MoE with 12B active, priced at RMB0.5 per million input tokens](https://hy.tencent.com/research/hy4-flash))

In a mixture-of-experts model a router sends each token to a few experts, so the forward pass costs about 2 FLOPs per active parameter, while every expert still has to be stored in accelerator memory. Memory therefore scales with total parameters and per-token compute with active parameters. A 2.4T-total MoE with about 70B active needs the per-token FLOPs of a dense 70B model but roughly 34 times the weight memory, which forces multi-node expert parallelism and makes all-to-all communication a key cost. This is why MoE prices per token can be low while the hardware footprint is large, and why small-batch decoding is memory-bandwidth-bound: each step reads many experts' weights for few tokens. The snippet uses round illustrative numbers and ignores KV cache and activations.

$$
M_{\text{weights}} \approx N_{\text{total}}\, b,\qquad F_{\text{token}} \approx 2 N_{\text{active}}
$$

```python
# MoE serving arithmetic with illustrative round numbers (not a real model's config).
def moe(total_b, active_b, bytes_per_param, tokens_per_s):
    weights_gb = total_b * bytes_per_param           # every expert must sit in memory
    flops_per_tok = 2 * active_b * 1e9               # ~2 FLOPs per active parameter per token
    return weights_gb, flops_per_tok, flops_per_tok * tokens_per_s / 1e15

for name, tot, act in [("big MoE", 2400, 70), ("mid MoE", 220, 12), ("dense 70B", 70, 70)]:
```
