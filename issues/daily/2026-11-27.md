### L1 · Price a multi-turn chat: quadratic re-reads and what a prefix cache saves

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~12 min

**Why today.** DeepSeek's test cost card splits each turn into cache-hit input (0.02 yuan/M), cache-miss input (1 yuan/M) and output (4 yuan/M), which is exactly the structure that decides what a long chat costs. ([DeepSeek tests a per-turn 'usage consumed' card showing tokens and API-priced cost in its free chat app](https://www.ithome.com/1/033/157.htm))

A stateless chat API re-sends the full history every turn, so with per-turn length growing roughly linearly the total prompt tokens over n turns grow like n^2/2. Prefix (KV) caching stores the attention keys and values for an already-seen prefix, so only the new suffix has to be prefilled; providers pass that saving on as a much lower cache-hit price. When hits are 50x cheaper than misses, the cached cost of a long chat is dominated by output tokens and the new user message, and the saving over no cache grows with conversation length. It breaks when the prefix changes (an edited system prompt, a reordered tool list, a timestamp near the top), when the cache entry is evicted after idle time, or when requests land on a replica without the entry.

$$
T_{prompt}(n)=\sum_{k=1}^{n}\big(S+kU+(k-1)R\big)\approx \tfrac{n^2}{2}(U+R);\quad C=\sum_k \big(h_k p_{hit}+m_k p_{miss}+R\,p_{out}\big)
$$

```python
# Cost of a multi-turn chat when every turn re-sends the whole history.
# Prices: the off-peak rates reported for DeepSeek's cost card (yuan per million tokens).
# Conversation sizes are illustrative.
HIT, MISS, OUT = 0.02, 1.0, 4.0
SYS, USER, REPLY = 2_000, 150, 600   # tokens: system prompt, each user msg, each reply

def chat_cost(turns, cached=True):
    hist, total, prompt_tokens = SYS, 0.0, 0
    for _ in range(turns):
        prompt = hist + USER                 # model re-reads everything so far
        hit = hist if cached else 0          # prefix from earlier turns is in the cache
        miss = prompt - hit
        total += (hit * HIT + miss * MISS + REPLY * OUT) / 1e6
        prompt_tokens += prompt
        hist = prompt + REPLY
    return total, prompt_tokens

for n in (1, 10, 40):
    c, p = chat_cost(n, True); u, _ = chat_cost(n, False)
    print(f"{n:>2} turns: {p:>9,} prompt tokens | cached {c:.4f} yuan | no cache {u:.4f} yuan | x{u/c:.1f}")
```

### L2 · Keep agent prompts append-only so new tools don't invalidate the cache

`Agent / harness engineering` · now 4.0 → target 5.0 · priority 0.70 · ~10 min

**Why today.** DeepSeek's documented deferred tool loading appends new tool definitions to the end of the conversation so the existing prompt-cache prefix stays valid. ([DeepSeek documents deferred tool loading in its API so agents can add tools without breaking the prompt cache](https://api-docs.deepseek.com/guides/tool_calls/))

Prefix caches match on the longest identical token prefix, so any change near the top of a prompt forces everything after it to be recomputed. The classic layout puts all tool schemas in the header; adding one tool mid-session then invalidates the whole history behind it. Appending the new definition after the history costs only its own tokens. The trade-off is that models may attend less reliably to instructions buried late in a long context, and providers must support tools declared outside the header. The same rule covers dynamic system-prompt text: put anything volatile (dates, user state, retrieved snippets) after the stable part.

```python
# Why deferred tools are APPENDED: a prefix cache reuses only the longest common prefix.
# Token lists are toy stand-ins; each tool schema is ~800 tokens (illustrative).
def common_prefix(a, b):
    n = 0
    for x, y in zip(a, b):
        if x != y: break
        n += 1
    return n

system = ["sys"] * 1500
tools = {t: [t] * 800 for t in ("search", "calendar", "email", "sql")}
history = ["msg"] * 6000            # conversation so far
new_tool = tools["sql"]

base = system + tools["search"] + tools["calendar"] + tools["email"] + history
front = system + new_tool + tools["search"] + tools["calendar"] + tools["email"] + history  # tool spliced into the header
append = base + new_tool             # tool definition added at the end

for name, p in (("insert in header", front), ("append at end", append)):
    reused = common_prefix(base, p)
    print(f"{name:17s}: prompt {len(p):>5} tokens, cache reuse {reused:>5}, recompute {len(p) - reused:>5}")
```

### L3 · Evaluate a medical chatbot by PPV at realistic prevalence, not accuracy alone

`LLM / agent evaluation` · now 2.5 → target 4.5 · priority 2.00 · ~10 min

**Why today.** People's Daily cites a case where Doubao read a bleed into a CT that showed none, and says the app handles more than 20 million health consultations a day. ([People's Daily warns 'don't treat Doubao as a doctor', saying it fields 20M+ health queries a day](https://www.thepaper.cn/newsDetail_forward_34573063))

Sensitivity and specificity describe a test given the true condition, but a user cares about the positive predictive value: the chance the condition is present given that the system says so. By Bayes' rule PPV depends on prevalence, so a screener with 95% sensitivity and 90% specificity is right about most positives in a referral clinic but wrong about almost all of them when only 1 in 1,000 askers has the condition. At tens of millions of queries a day, even a small false-positive rate means a very large absolute number of false alarms, while the negative predictive value looks reassuringly close to 100% simply because negatives dominate. An evaluation should therefore report sensitivity, specificity and PPV/NPV at the prevalence of the actual user population, stratified by condition, rather than a single accuracy on a balanced benchmark.

$$
\mathrm{PPV}=\frac{s\,\pi}{s\,\pi+(1-c)(1-\pi)}
$$

```python
# A symptom checker with 'good' accuracy still mostly raises false alarms when the condition is rare.
# Sensitivity, specificity and prevalences are illustrative, not measured figures for any product.
def ppv(sens, spec, prev):
    tp = sens * prev
    fp = (1 - spec) * (1 - prev)
    return tp / (tp + fp)

def npv(sens, spec, prev):
    tn = spec * (1 - prev)
    fn = (1 - sens) * prev
    return tn / (tn + fn)

sens, spec = 0.95, 0.90
for prev in (0.30, 0.05, 0.01, 0.001):
    print(f"prevalence {prev:>6.1%}: PPV {ppv(sens, spec, prev):6.1%}  NPV {npv(sens, spec, prev):7.3%}  "
          f"false alarms per 1M queries {round((1-spec)*(1-prev)*1e6):>7,}")
```
