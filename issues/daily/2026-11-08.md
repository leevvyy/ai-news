### L1 · Size a quantised MoE's memory, and test a 'fits in 64 GB' claim

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~15 min

**Why today.** The llama-modchip README claims a 284.33B-parameter MoE at 1.71 bits per weight fits in 64 GB, which is a checkable arithmetic claim. ([llama-modchip claims DeepSeek-V4-Flash (284B MoE) runs CPU-only in 64 GB RAM at about 9-15 tok/s](https://github.com/synchopate/llama-modchip))

Weight memory is parameters times bits per weight divided by 8, so 284.33B at 1.71 bpw is about 56.6 GiB, matching the README's 56.56 GiB. At 3 bits the same model needs about 99 GiB, so only extreme quantisation fits. In an MoE all experts must be resident, so memory scales with total parameters, but each decoded token reads only the active parameters. Decode is therefore memory-bandwidth-bound and tok/s is at most bandwidth divided by active-weight bytes. This ignores KV cache, dequantisation compute and routing cache misses, and says nothing about quality loss at 1.71 bits.

$$
M_{w} = \frac{N_{total}\, b}{8}, \qquad \text{tok/s} \lesssim \frac{BW}{N_{active}\, b / 8}
$$

```python
# Illustrative numbers: weight memory for a MoE at a given bits-per-weight (bpw).
def weight_gib(params_b, bpw):
    return params_b * 1e9 * bpw / 8 / 2**30

def fits(total_b, bpw, ram_gib, kv_gib, os_gib=3.0):
    need = weight_gib(total_b, bpw) + kv_gib + os_gib
    return need, need <= ram_gib

for bpw in (16, 8, 4, 3, 1.71):
    need, ok = fits(284.33, bpw, 64, kv_gib=1.0)
    print(f"{bpw:>5} bpw: weights {weight_gib(284.33,bpw):7.1f} GiB, total {need:7.1f} GiB, fits 64 GiB: {ok}")
# Decode is memory-bound: each token reads the ACTIVE weights once.
active_b, bpw, bw_gbs = 13.17, 1.71, 90.0   # assumed DDR5 bandwidth, GB/s
bytes_tok = active_b * 1e9 * bpw / 8
print(f"upper bound decode: {bw_gbs*1e9/bytes_tok:.1f} tok/s at {bw_gbs} GB/s")
```
