### L1 · Check whether a one-point benchmark gap is signal or noise

`LLM / agent evaluation` · now 2.5 → target 4.5 · priority 2.00 · ~15 min

**Why today.** Google reports Gemini 4 Neon at 65.2% on Terminal-Bench 4.1, and search snippets say Claude Opus 5.5 scores slightly higher. Before reading a ranking into that, it helps to know how many tasks it takes to separate two pass rates. ([Google launches Gemini 4 Neon, a $3/$15 coding and agent model it says tops Artificial Analysis' Coding Agent Index](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/))

A pass rate on n tasks is a binomial proportion, so its standard error is sqrt(p(1-p)/n). That is about 5 points at n=89 and still about 1.5 points at n=1000. When two models run the same tasks, the gap's variance is reduced by the per-task correlation rho of their outcomes, because both tend to solve the same easy tasks. That is why paired comparisons are tighter than comparing two separate confidence intervals. Even so, resolving a 1.3-point gap at z=2 needs thousands of tasks unless rho is very high. Agentic benchmarks add run-to-run variance from sampling and the harness, so multiple seeds per task matter too. The Wilson interval is better than the normal approximation when p is near 0 or 1 or n is small.

$$
\mathrm{SE}(\hat p_A-\hat p_B)=\sqrt{\tfrac{p_A(1-p_A)+p_B(1-p_B)-2\rho\sqrt{p_A(1-p_A)p_B(1-p_B)}}{n}}
$$

```python
import math
# Is a benchmark gap real? Illustrative pass rates, not any vendor's actual per-task data.
def wilson(p, n, z=1.96):
    c = p + z*z/(2*n); h = z*math.sqrt(p*(1-p)/n + z*z/(4*n*n)); d = 1 + z*z/n
    return (c - h)/d, (c + h)/d
def gap_se(pa, pb, n, rho):
    # SE of pa - pb when both models run the SAME n tasks; rho = per-task outcome correlation
    va, vb = pa*(1-pa)/n, pb*(1-pb)/n
    return math.sqrt(va + vb - 2*rho*math.sqrt(va*vb))
pa, pb = 0.652, 0.665   # model A vs model B: a 1.3-point gap
for n in (89, 300, 1000):
    lo, hi = wilson(pa, n)
    print(f"n={n:5d}  A 95% CI [{lo:.3f}, {hi:.3f}]", end="")
    for rho in (0.0, 0.6):
        z = (pb - pa)/gap_se(pa, pb, n, rho)
        print(f"  rho={rho}: z={z:.2f}", end="")
    print()
# tasks needed to resolve a 1.3-pt gap at z=2 with paired rho=0.6
se_needed = (pb - pa)/2
v = pa*(1-pa) + pb*(1-pb) - 2*0.6*math.sqrt(pa*(1-pa)*pb*(1-pb))
print("tasks needed:", math.ceil(v/se_needed**2))
```

### L2 · Estimate MoE decode speed when experts are streamed from SSD

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~10 min

**Why today.** Hugging Face describes running a 180B-parameter MoE in Transformers on 32GB of RAM by loading experts from disk, so it is worth knowing what limits the speed of that approach. ([Hugging Face shows a 180B-parameter MoE running in Transformers on 32GB of RAM by streaming experts from disk](https://huggingface.co/blog/moe-expert-streaming))

In a top-k MoE each token touches k of E experts per layer, so per-token weight traffic is about L*k*bytes_per_expert, not the full model. If experts live on SSD, decode speed is roughly bandwidth divided by bytes missed per token, so an expert cache in RAM helps in proportion to its hit rate. Under uniform routing the hit rate is just cache/E, which makes small caches nearly useless. Real routers are skewed and consecutive tokens reuse experts, so measured hit rates are higher, and that skew is what makes streaming practical. Prefetching the next layer's experts while the current one computes can hide part of the latency, but not the bandwidth. The numbers below are illustrative and do not describe the model in the post.

$$
\text{tok/s}\approx\frac{B_{\text{SSD}}}{L\,k\,(1-h)\,S_{\text{expert}}}
$$

```python
# Expert streaming: how fast can a MoE decode when experts live on SSD? Illustrative config, not a real model.
L, E, k = 60, 128, 8           # layers, experts per layer, experts active per token
expert_bytes = 11e6            # one expert at 4-bit: 60*128*11MB ~ 84 GB ~ 170B params (illustrative)
ssd_bw = 6e9                   # NVMe read bandwidth, bytes/s
for cache_per_layer in (0, 8, 16, 32):
    # assume uniform routing: P(an active expert is already cached) = cache/E
    miss = 1 - cache_per_layer/E
    bytes_per_token = L * k * miss * expert_bytes
    tps = ssd_bw / bytes_per_token
    ram_gb = L * cache_per_layer * expert_bytes / 1e9
    print(f"cache {cache_per_layer:3d}/layer  RAM for experts {ram_gb:5.1f} GB  "
          f"read {bytes_per_token/1e9:5.2f} GB/token  ~{tps:5.2f} tok/s")
print("total expert weights:", round(L*E*expert_bytes/1e9, 1), "GB")
```
