### L1 · Measure shadow-traffic parity and bound the mismatch rate with a Wilson interval

`LLM / agent evaluation` · now 2.5 → target 4.5 · priority 2.00 · ~15 min

**Why today.** Anthropic checked its Rust rewrite by shadowing production traffic, replaying each model output into the new path and reducing mismatches to text-free fingerprints. ([Anthropic moves its Messages API from Python to Rust with Claude agents, cutting CPU per request ~70%](https://www.anthropic.com/research/migrating-api-to-rust))

Shadow (differential) testing runs the old and new systems on the same inputs and compares outputs. Comparing a fingerprint of the response structure (field names, types, lengths) instead of the raw text catches most behavioural bugs without anyone reading user content, but it misses bugs that change values while keeping the shape. The mismatch count over n requests is binomial, so report the rate with a confidence interval: the Wilson interval behaves well near 0, unlike the normal approximation, which can go negative. With zero mismatches, the 'rule of three' gives a 95% upper bound of about 3/n, which tells you how much traffic you need before claiming parity at a given level. Mismatches are rarely independent in practice: a bug hitting one customer's request pattern clusters, so stratify by endpoint or tenant before trusting a pooled rate.

$$
\tilde p = \frac{\hat p + \frac{z^2}{2n}}{1+\frac{z^2}{n}},\quad \tilde p \pm \frac{z}{1+\frac{z^2}{n}}\sqrt{\frac{\hat p(1-\hat p)}{n}+\frac{z^2}{4n^2}};\quad k=0 \Rightarrow p_{95} \approx 3/n
$$

```python
# Shadow-traffic parity: estimate the mismatch rate between an old and a new implementation
# and put a Wilson confidence interval on it. Illustrative synthetic data only.
import hashlib, json, math, random
random.seed(1)

def fingerprint(resp):  # hash the structure (keys, types, lengths), not the text itself
    shape = {k: (type(v).__name__, len(v) if isinstance(v, (str, list)) else v if isinstance(v, (int, bool)) else None)
             for k, v in sorted(resp.items())}
    return hashlib.sha256(json.dumps(shape, sort_keys=True).encode()).hexdigest()[:12]

def old_impl(req):
    return {"id": req, "stop_reason": "end_turn", "content": "x" * (req % 50), "usage": req % 7}

def new_impl(req):
    r = old_impl(req)
    if random.random() < 0.004:      # injected bug: wrong stop_reason in ~0.4% of requests
        r["stop_reason"] = "max_tokens_x"
    return r

def wilson(k, n, z=1.96):
    p = k / n; d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return c - h, c + h

n = 20000
bad = sum(fingerprint(old_impl(i)) != fingerprint(new_impl(i)) for i in range(n))
lo, hi = wilson(bad, n)
print(f"mismatches {bad}/{n} = {bad/n:.4%}, 95% Wilson CI [{lo:.4%}, {hi:.4%}]")
# Rule of three: with 0 mismatches in n requests, the 95% upper bound is ~3/n.
print(f"zero-mismatch upper bound for n={n}: {3/n:.4%}")
```

### L2 · Size a KV cache and see why an SSD tier trades capacity for reload latency

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~12 min

**Why today.** Kioxia and Nvidia showed 144 SSDs adding about 1.1 PB to a GB200 NVL72 rack to extend effective high-bandwidth memory capacity. ([Kioxia and Nvidia show SSDs stretching a GB200 NVL72 rack's memory to ~1.1 PB; Kioxia shares jump 12.6%](https://www.kioxia.com/en-jp/business/news/2026/20261126-1.html))

During decoding, each layer caches a key and a value vector per KV head for every past token, so KV memory grows linearly with context length and batch size. Grouped-query attention cuts it by sharing KV heads across query heads, which is why n_kv rather than the query-head count appears in the formula. Long-context serving is usually limited by HBM capacity, not compute, and tiering cold KV blocks to host RAM or flash multiplies how many sessions you can keep warm. The cost is bandwidth: reloading a 40 GB cache from one NVMe drive takes seconds, so flash tiers only pay off when reads are striped across many drives and prefetched before the session resumes. The snippet's model and drive numbers are illustrative, not any real model's or Kioxia's specs.

$$
M_{KV} = 2\,L\,n_{kv}\,d_{head}\,T\,b,\qquad t_{reload} = M_{KV} / (B_{drive} \cdot N_{drives})
$$

```python
# KV-cache sizing: how many concurrent long-context sequences fit in HBM, and how many more
# an SSD tier could hold. All model and hardware numbers are illustrative, not any real model's config.
L, n_kv, d_head, b = 80, 8, 128, 2          # layers, KV heads (GQA), head dim, bytes/elem (bf16)
T = 128_000                                 # tokens per sequence
per_token = 2 * L * n_kv * d_head * b       # K and V
per_seq = per_token * T
hbm_free = 72 * 80e9                        # e.g. 72 GPUs x 80 GB left after weights (illustrative)
ssd = 1.1e15                                # ~1.1 PB raw flash tier
print(f"KV per token: {per_token/1024:.0f} KiB, per 128k-token sequence: {per_seq/1e9:.1f} GB")
print(f"sequences resident in HBM: {int(hbm_free // per_seq)}")
print(f"sequences parked on SSD:   {int(ssd // per_seq)}")
# Bandwidth is the catch: reloading one sequence's KV from flash at an assumed 14 GB/s per drive
for drives in (1, 8, 144):
    print(f"reload time with {drives:>3} drives: {per_seq / (14e9 * drives) * 1000:.1f} ms")
```

### L3 · Turn a bond yield into an implied default probability, and see how sensitive it is

`Domain AI (finance, health)` · now 3.5 → target 4.5 · priority 0.70 · ~10 min

**Why today.** CoreWeave's Meta-backed GPU loan is talked at about 7-7.5% while its own unsecured 2031 bonds yield about 18%. ([CoreWeave's banks ready $4.5B Meta-backed GPU loan at ~7% while its own bonds yield ~18%](https://finance.yahoo.com/technology/ai/articles/coreweave-bankers-reportedly-ready-4-210216828.html))

In a reduced-form credit model, default arrives as a Poisson event with hazard rate lambda, and investors lose a fraction (1 - R) on default. To first order the spread over risk-free equals lambda(1 - R), so lambda is roughly s/(1 - R), and the probability of default by time t is 1 - exp(-lambda t). These are risk-neutral probabilities: they include a risk and liquidity premium, so they overstate real-world default odds, often by a lot for distressed names. The recovery assumption dominates the answer, and secured or contract-backed debt has a much higher R than unsecured bonds. Using the same R for both, as the snippet does to keep it simple, overstates the loan's implied risk. All inputs are illustrative assumptions, not CoreWeave's actual risk-free curve or recoveries.

$$
s \approx \lambda (1-R),\qquad P(\tau \le t) = 1 - e^{-\lambda t}
$$

```python
# From bond yield to implied default probability (reduced-form, risk-neutral, flat hazard).
# lambda ~ spread / (1 - R);  P(default within t) = 1 - exp(-lambda t). Illustrative inputs.
import math
risk_free = 0.040                 # assumed ~5-year Treasury yield (illustrative)
recovery = 0.40                   # assumed recovery rate for unsecured debt
for name, y in [("contract-backed loan", 0.0725), ("unsecured bond", 0.18)]:
    s = y - risk_free
    lam = s / (1 - recovery)
    for t in (1, 5):
        print(f"{name:21s} yield {y:.2%} spread {s:.2%} hazard {lam:.2%}/yr  P(default<{t}y) = {1-math.exp(-lam*t):.1%}")
# Sensitivity: the answer moves a lot with the recovery assumption
for R in (0.2, 0.4, 0.6):
    lam = (0.18 - risk_free) / (1 - R)
    print(f"R={R:.0%}: 5y default prob {1-math.exp(-5*lam):.1%}")
```
