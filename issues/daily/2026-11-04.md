### L1 · MoE: why compute follows active parameters but memory follows total

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~10 min

**Why today.** FlashProve's prover cost is described as scaling with the ~17B active parameters of a 400B mixture-of-experts model. ([Anthropic's FlashProve proves LLM outputs with a zkSNARK, at roughly 70-95x overhead on a 400B MoE](https://www.anthropic.com/research/provable-inference))

A mixture-of-experts layer routes each token to a few experts, so per-token FLOPs are about 2 times the active parameters, not the total. Every expert must still be resident in memory because any token may route to it, so weight memory scales with total parameters times bytes per weight. Hence an MoE can be cheap per token yet need a large accelerator pool or heavy quantisation to hold. The saving is not free: routing creates load imbalance and all-to-all communication, and small batches touch many experts, erasing the arithmetic advantage. The numbers below use the 400B/17B/4-bit figures from the item for illustration only; they are not measurements of any system.

$$
\text{FLOPs/token} \approx 2 N_{active}, \qquad M_{weights} = N_{total} b
$$

```python
# Illustrative MoE arithmetic (numbers from the FlashProve item; the rest is toy).
total, active = 400e9, 17e9
bytes_per_param = 0.5            # 4-bit weights
weights_gb = total * bytes_per_param / 1e9
flops_per_token = 2 * active     # ~2 FLOPs per active parameter per token
dense_flops = 2 * total
print(f"weights in memory: {weights_gb:.0f} GB (set by TOTAL params)")
print(f"compute/token: {flops_per_token/1e9:.0f} GFLOP vs dense {dense_flops/1e9:.0f} GFLOP")
print(f"MoE compute saving: {dense_flops/flops_per_token:.1f}x")
```
