### L1 · Publish a result others can reproduce bit for bit: seeds, reduction order and hashes

`Public output` · now 1.5 → target 4.0 · priority 1.00 · ~15 min

**Why today.** Unemployment Labs says a B300, given a recovered seed, reproduced DeepSeek-V4-Flash's initial weights bit for bit while an H100 and an MI300X did not. A public claim like that is only as strong as the recipe others can rerun. ([Forensic study says six top Chinese open models were initialised on export-banned Nvidia Blackwell chips](https://unemploymentlabs.com/checkpoint-forensics))

Floating-point addition is not associative, so the same seeded computation can give different bits when a kernel sums in a different order. Different GPUs, tile sizes and library versions all change that order. The seed fixes the random stream, but the hardware and kernel fix the arithmetic, which is why the weights end up carrying a hardware fingerprint. When you publish, release the seed, the exact code and library versions, the hardware and kernel settings, a SHA-256 of the output, and a short script that recomputes the hash; then a reader can verify your claim instead of trusting it. The limit is that bit-exactness proves only that the recipe matches. It says nothing about where or when the computation ran, so state your claim no more strongly than that.

$$
(a+b)+c \neq a+(b+c) \text{ in floating point, so } \mathrm{fl}\big(\textstyle\sum_i x_i\big) \text{ depends on the summation order}
$$

```python
# Why bit-exact reproduction needs the same seed AND the same reduction order (illustrative)
import hashlib, random, struct
def init_weights(seed, n=4096):
    rng = random.Random(seed)
    return [rng.gauss(0.0, 0.02) for _ in range(n)]
def digest(xs):
    return hashlib.sha256(b"".join(struct.pack("<d", x) for x in xs)).hexdigest()[:16]
def reduce_seq(xs):                       # left-to-right sum
    s = 0.0
    for x in xs: s += x
    return s
def reduce_tree(xs, width=32):            # blocked sum, like a GPU warp/tile reduction
    partial = [reduce_seq(xs[i:i + width]) for i in range(0, len(xs), width)]
    return reduce_seq(partial)
w1, w2, w3 = init_weights(7), init_weights(7), init_weights(8)
print("same seed, same hash :", digest(w1) == digest(w2), digest(w1))
print("other seed           :", digest(w3))
a, b = reduce_seq(w1), reduce_tree(w1)
print(f"sequential sum {a!r}\nblocked sum    {b!r}\nbit-identical? {a == b}")
# Publish: seed, code version, hardware/kernel, and the hash, plus a script that recomputes it.
```

### L2 · Separate MoE memory from MoE compute, and check an SSD-streaming speed claim

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~15 min

**Why today.** AutoArk says Edge0-145B, a sparse MoE with about 10B active parameters, runs on a laptop at a 29 GB peak and more than 80 tokens/s by streaming weights from SSD. ([Beijing startup AutoArk open-sources Edge0-145B, a 145B MoE model it says runs on a laptop in 29 GB](https://github.com/Edge0-AI/edge0))

In a mixture-of-experts model, the per-token FLOPs scale with the active parameters, but the memory needed scales with all parameters, because any expert may be routed to. Weight bytes are about N·b/8. At roughly 4.5 effective bits (FP4 plus scales), 145B parameters is about 82 GB. A 29 GB peak therefore keeps only about a third of the weights resident, and the router's choices decide how often a token needs an expert that is still on disk. Every such miss costs SSD bandwidth, so throughput is capped near B_SSD/(miss rate × active bytes). With illustrative numbers (7 GB/s, 10% misses) the cap is about 12 tok/s, so a claim of 80+ tok/s implies the misses are well below about 2%: experts must be very predictable or very well cached. Expert locality is therefore the number to ask for when you evaluate an on-device MoE claim.

$$
M_W \approx N_{\text{total}}\,\tfrac{b}{8},\qquad \text{tok/s} \lesssim \frac{B_{\text{SSD}}}{m\,N_{\text{active}}\,b/8}
$$

```python
# Memory vs compute for a sparse MoE (illustrative numbers taken from one vendor claim)
def gb(params, bits):
    return params * bits / 8 / 1e9
total, active = 145e9, 10e9          # Edge0-145B as reported: 145B total, ~10B active per token
for name, bits in [("bf16", 16), ("int8", 8), ("~4.5-bit (FP4 + scales)", 4.5)]:
    print(f"{name:24s} all weights {gb(total, bits):6.1f} GB | active slice {gb(active, bits):5.1f} GB")
resident_gb = 29.0                     # reported peak memory
frac = resident_gb / gb(total, 4.5)
print(f"resident fraction at ~4.5 bits: {frac:.0%} of weights; the rest must stream from SSD")
# If a token touches experts that are not resident, it must read them from disk:
ssd_gbps, miss_rate = 7.0, 0.10      # illustrative NVMe bandwidth and expert-miss fraction
bytes_per_tok = gb(active, 4.5) * miss_rate
print(f"SSD reads/token {bytes_per_tok*1e3:.0f} MB -> SSD-bound ceiling {ssd_gbps/bytes_per_tok:.0f} tok/s")
```

### L3 · Turn a data-centre gigawatt figure into accelerator counts and yearly training FLOPs

`DL model training` · now 3.0 → target 4.5 · priority 1.35 · ~12 min

**Why today.** SpaceX's Arizona campus is described as up to 6 GW, and a power figure is the most common, and most misread, way compute is announced. ([SpaceX plans more than $74B of AI supercomputing campuses in Arizona and Texas](https://thehill.com/policy/technology/6217630-spacex-plans-data-centers-texas-arizona/))

Site power covers more than chips. Divide by PUE (cooling and conversion overhead, often 1.1–1.4) to get the IT load. Then divide by the all-in power per accelerator, which includes its share of CPUs, networking and storage, to get a device count. Multiply by peak FLOP/s, model FLOPs utilisation (MFU, often 30–45% for large training runs) and seconds per year to get usable training compute, and compare it with C ≈ 6ND for a dense model of N parameters on D tokens. Each factor is uncertain by tens of percent, so report a range rather than a point. Announced capacity is a ceiling, not a commitment: campuses come online in phases.

$$
N_{acc} = \frac{P_{site}}{\mathrm{PUE}\cdot p_{acc}},\qquad C_{yr} = N_{acc}\, F_{peak}\, \mathrm{MFU}\, t_{yr},\qquad C_{train}\approx 6ND
$$

```python
# From a campus power figure to an order-of-magnitude accelerator count (illustrative assumptions)
def accelerators(site_gw, pue, kw_per_accel_all_in):
    it_kw = site_gw * 1e6 / pue                  # power left for IT load
    return it_kw / kw_per_accel_all_in
site_gw = 6.0                                     # reported upper bound for the Arizona campus
for pue in (1.1, 1.3):
    for kw in (1.8, 2.5):                         # accelerator + share of CPU, network, storage
        n = accelerators(site_gw, pue, kw)
        print(f"PUE {pue}, {kw} kW/accel -> {n/1e6:.2f}M accelerators")
# Training compute per year at a utilisation (MFU) assumption:
peak_flops, mfu = 2.5e15, 0.35                    # illustrative dense BF16 peak per accelerator
n = accelerators(site_gw, 1.2, 2.2)
print(f"~{n*peak_flops*mfu*3.15e7:.1e} FLOP/yr at {mfu:.0%} MFU")
```
