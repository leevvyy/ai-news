### L1 · Turn a data-centre power budget into training compute and model size

`DL model training` · now 3.0 → target 4.5 · priority 1.35 · ~15 min

**Why today.** Alibaba says US chip-access rules may force it to revise its target of more than 20 GW of capacity by 2032. A power target is really a compute target, and the chain from watts to trainable parameters shows what such a cut costs. ([Alibaba warns new US chip-access rules may force it to cut its 20 GW data-centre target and capex plans](https://www.benzinga.com/markets/earnings/26/11/63429551/alibabas-ai-engine-is-roaring-but-us-chip-curbs-threaten-to-hit-the-brakes) · [Alibaba September-quarter revenue rises 10% as AI cloud grows 53%; Qwen unit's loss triples to RMB10.5bn](https://finance.yahoo.com/markets/stocks/articles/alibaba-group-announces-september-quarter-100200549.html))

Facility power divided by PUE gives IT power, and IT power divided by all-in watts per accelerator gives a device count. Multiply by peak FLOP/s and model FLOPs utilisation (MFU, typically 30-50% for large dense or MoE training) to get sustained FLOP/s, then by wall-clock time to get a run's compute C. For a dense transformer, training costs about C = 6ND FLOPs for N parameters and D tokens, and the Chinchilla fit puts the compute-optimal ratio near D/N = 20, so N grows as sqrt(C). That square root is why a 40% power cut costs only about 23% in compute-optimal model size, though it costs the full 40% in throughput for inference. The chain breaks where its assumptions do: MoE models count only active parameters in 6ND, production runs are deliberately over-trained past Chinchilla for cheaper inference, and interconnect or memory limits can cap MFU well below the chip's peak.

$$
C = \frac{P_{site}}{\mathrm{PUE}\, W_{acc}}\, F_{peak}\, \mathrm{MFU}\, t, \qquad C \approx 6ND,\; D \approx 20N \Rightarrow N \approx \sqrt{C/120}
$$

```python
# From gigawatts to a training run. All hardware numbers are illustrative, not any company's.
P_site = 1e9          # 1 GW of facility power
PUE = 1.3             # facility overhead: cooling, conversion losses
W_per_accel = 1800.0  # all-in IT watts per accelerator (chip + host + network share)
peak = 2.5e15         # dense BF16 FLOP/s per accelerator (illustrative)
for mfu in (0.30, 0.45):
    n = P_site / PUE / W_per_accel
    flops = n * peak * mfu                      # sustained FLOP/s for the whole site
    days = 90
    C = flops * days * 86400                    # FLOPs in a 90-day run
    # Chinchilla-style compute-optimal split: C = 6 N D with D = 20 N
    N = (C / 120) ** 0.5
    D = 20 * N
    print(f"MFU {mfu:.0%}: {n/1e3:,.0f}k accelerators, {flops:.2e} FLOP/s, "
          f"90-day C = {C:.2e} FLOP -> N = {N/1e12:.1f}T params, D = {D/1e12:.0f}T tokens")
# Same site, but only 60% of the planned power is built (a cut target):
print("power cut to 60% scales C by 0.6 and compute-optimal N by", round(0.6**0.5, 3))
```

### L2 · Scope every agent cache, memory and credential to the principal

`Agent / harness engineering` · now 4.0 → target 5.0 · priority 0.70 · ~10 min

**Why today.** Reuters reports Meta staff saw the Muse agent surface messages from other people's accounts, which Meta says were mostly hallucinations. Whatever the cause there, cross-account bleed is a classic failure mode worth designing out as agents like Gemini's new Mac computer use gain access to personal data. ([Reuters: Meta staff flag its Muse AI agent mixing up users' conversations and exposing private data](https://www.investing.com/news/stock-market-news/as-meta-bets-big-on-muse-ai-agent-early-safety-mishaps-surface-5035458) · [Google adds computer use to the Gemini Mac app, running tasks in a background window for paid US users](https://9to5google.com/2026/11/19/gemini-mac-computer-use/))

An agent has more shared state than a chatbot: response and tool-result caches, long-term memory stores, retrieval indexes, and the credentials its tools use. If any of these is keyed on content alone (the prompt, a URL, a query embedding), two users who send the same request can receive each other's results, because the output depended on who asked but the key did not. The fix is to treat the principal (user, tenant, session) as part of every key and every row, to filter retrieval by principal before ranking rather than after, and to mint tool credentials per principal with least privilege, so a confused agent cannot read what its token cannot reach. Caching stays safe for genuinely public, user-independent results, but that must be an explicit decision. Tests should replay identical requests from two principals and assert that their outputs share nothing private.

```python
# Cross-account leakage from a cache keyed on content alone, and the fix: key on the principal too.
import hashlib
class Cache:
    def __init__(self, scoped): self.d, self.scoped = {}, scoped
    def key(self, user, prompt):
        parts = (user, prompt) if self.scoped else (prompt,)
        return hashlib.sha256("\x1f".join(parts).encode()).hexdigest()
    def get_or_run(self, user, prompt, run):
        k = self.key(user, prompt)
        if k not in self.d:
            self.d[k] = run(user, prompt)
        return self.d[k]
def agent(user, prompt):  # stand-in for a tool-using agent that reads the user's own inbox
    inbox = {"alice": "Alice: biopsy results Friday", "bob": "Bob: no new messages"}
    return f"[{user}] summary of inbox -> {inbox[user]}"
for scoped in (False, True):
    c = Cache(scoped)
    c.get_or_run("alice", "summarise my messages", agent)
    out = c.get_or_run("bob", "summarise my messages", agent)
    leak = "Alice" in out
    print(f"scoped={scoped}: bob sees -> {out!r}  LEAK={leak}")
# Rule: every key, memory row and tool credential carries the principal; prompts are not identities.
```

### L3 · Estimate serving cost per token from memory bandwidth and batch size

`LLM internals & post-training` · now 2.5 → target 4.5 · priority 2.00 · ~12 min

**Why today.** Alibaba blamed the widening RMB10.5bn loss in the segment that houses Qwen partly on Qwen app inference costs. The cost of a consumer chatbot comes down to how many tokens each accelerator-hour produces. ([Alibaba September-quarter revenue rises 10% as AI cloud grows 53%; Qwen unit's loss triples to RMB10.5bn](https://finance.yahoo.com/markets/stocks/articles/alibaba-group-announces-september-quarter-100200549.html))

In autoregressive decoding each step produces one token per sequence but must stream all active weights from HBM, plus each sequence's KV cache. At batch 1 the arithmetic units sit idle and throughput is roughly bandwidth / weight bytes, so decode is memory-bound. Batching amortises the weight read across sequences, so tokens per second rise almost linearly at first. That is why providers batch aggressively and why free consumer traffic with long contexts is expensive. The KV term grows with batch times context, so it eventually dominates and throughput saturates. That is the motivation for grouped-query or multi-head latent attention, KV quantisation, and paged KV memory. The model ignores prefill (compute-bound), latency targets that cap batch size, and speculative decoding; treat it as a first-order bound, not a price quote.

$$
\text{tok/s} \approx B\, \frac{BW}{N_{act} b_w + B\, T\, m_{KV}}, \qquad \$/\text{M tok} = \frac{10^6\, p_{hr}}{3600\, \text{tok/s}}
$$

```python
# Why serving a chat app costs real money: decode is memory-bandwidth bound.
# Illustrative numbers only; not any vendor's model or GPU.
HBM = 4.0e12          # bytes/s of memory bandwidth per accelerator
gpu_hour = 3.0        # $ per accelerator-hour
active = 30e9         # active params per token (an MoE's activated experts)
bytes_per_w = 1       # FP8 weights
kv_per_tok = 70e3     # KV-cache bytes per token of context (layers x heads x dim x 2 x bytes)
ctx = 8000            # tokens of context per sequence
for batch in (1, 16, 128):
    # each decode step streams the weights once (shared by the batch) + each sequence's KV cache
    bytes_step = active * bytes_per_w + batch * ctx * kv_per_tok
    steps = HBM / bytes_step                      # decode steps per second
    tok_s = steps * batch
    cost = gpu_hour / (tok_s * 3600) * 1e6        # $ per million output tokens
    print(f"batch {batch:4d}: {tok_s:8.0f} tok/s, ${cost:7.2f} per M output tokens")
```
