### L1 · Size a worker pool for a router: why latency explodes past utilisation 1

`Agent / harness engineering` · now 4.0 → target 5.0 · priority 0.70 · ~15 min

**Why today.** DeepSeek's prototype has a router that dispatches tickets to isolated worker sessions, which makes the worker count a queueing-capacity question. ([DeepSeek open-sources Super-agent prototype: a Router and Worker design for autonomous coding agents](https://github.com/deepseek-ai/dsh-superagent-prototype))

Treat the router as a dispatcher feeding c workers, with triggers arriving at rate lambda and each task taking mean time s. Utilisation is rho = lambda*s/c. While rho < 1 the queue is stable and waits stay small; as rho approaches 1 waits blow up, and above 1 they grow without bound. The simulation below uses illustrative numbers only (3-minute tasks, Poisson arrivals): 4 workers cope with 1 trigger/min (rho 0.75) but collapse at 5/min, while 16 workers cope with 5/min (rho 0.94, p95 wait about 5 minutes) but not 10/min. Batching or deduplicating triggers lowers lambda; adding workers raises c. It breaks when tasks are not exchangeable, e.g. long tasks blocking a worker or tasks with dependencies.

$$
\rho = \frac{\lambda s}{c}, \qquad \rho < 1 \Rightarrow \text{stable queue}
$$

```python
import random, heapq
def sim(rate_per_min, workers, svc_min=3.0, n=20000, seed=1):
    random.seed(seed); t=0; free=[0.0]*workers; heapq.heapify(free); waits=[]
    for _ in range(n):
        t += random.expovariate(rate_per_min)
        start = max(t, heapq.heappop(free))
        heapq.heappush(free, start + random.expovariate(1/svc_min))
        waits.append(start - t)
    waits.sort(); return sum(waits)/n, waits[int(.95*n)]
for lam in (1, 5, 10):
    for w in (4, 16):
        m, p95 = sim(lam, w)
        print(f"lambda={lam:>2}/min workers={w:>2}  mean wait={m:7.2f} min  p95={p95:7.2f} min")
```

### L2 · Emulate a CPU as a next-state table, and see what memorising misses

`AI-off fluency` · now 2.5 → target 4.0 · priority 1.50 · ~15 min

**Why today.** Nesformer has a model predict a CPU's execution log one token at a time; this exercise writes the same idea by hand at toy scale. ([Nesformer compiles an NES CPU into the weights of a stock Qwen3.5 model](https://github.com/dbreunig/nesformer))

A deterministic machine is a function from state to next state, so its execution log is a sequence a next-token predictor can reproduce exactly. Below, a four-instruction accumulator CPU generates a golden log, and a dictionary 'model' memorises state to next-state pairs from it. Replay matches exactly, which is the nestest-style check. But a different program (LDI 6) visits states the table never saw, so it fails: exact emulation requires encoding the transition rule, not just the observed transitions. Toy CPU and table are illustrative and say nothing about how nesformer's weights are constructed.

```python
# Tiny accumulator CPU whose execution log is a token stream.
PROG = [("LDI",5),("ADD",3),("SUB",1),("JNZ",1),("HLT",0)]
def step(s):
    pc,a,z = s; op,x = PROG[pc]
    if op=="LDI": a=x
    elif op=="ADD": a=(a+x)&255
    elif op=="SUB": a=(a-x)&255
    pc = x if (op=="JNZ" and a!=0) else pc+1
    z = int(a==0)
    return (pc,a,z)
def run(n):
    s=(0,0,0); log=[s]
    while PROG[s[0]][0]!="HLT" and len(log)<n:
        s=step(s); log.append(s)
    return log
golden = run(40)
# "Model" = a lookup table learned from the golden log: state -> next state
table = {a:b for a,b in zip(golden, golden[1:])}
state, out = golden[0], [golden[0]]
while state in table and len(out)<len(golden):
    state = table[state]; out.append(state)
print(len(golden), "steps; replay matches golden:", out==golden)
print("distinct transitions:", len(table))
PROG[0] = ("LDI", 6)   # new program: the memorised table has never seen these states
new = run(40)
print("unseen transitions in new run:", sum(1 for a in new[:-1] if a not in table))
```
